## EtherCAT bridge: state, data and cleanup

`EtherCATBridge` receives interface, device name and XML path as positional constructor/CLI arguments. It checks interface presence/carrier, opens the pysoem master, scans slaves, selects a name match or falls back to slave zero, calls `config_map`, transitions PREOP/SAFEOP/OP, and clears outputs before marking itself initialized. The XML path is retained as an attribute but the bridge does not parse the XML; its 16-input/16-output layout is hardcoded. The supplied ESI identifies XHS_ECT_MD1616_V2.0, two output bytes and two input bytes, with a 200 ms BackToSafeopTimeout. Evidence: bridge `scripts/ethercat_bridge.py:L25-L58`, `scripts/ethercat_bridge.py:L112-L140`, `scripts/ethercat_bridge.py:L223-L423`; `XHS_ECT_050_v2.0 2.xml:L19-L56`, `XHS_ECT_050_v2.0 2.xml:L57-L105`.

| JSON command | Handler and effect |
|---|---|
| `init` | Opens raw interface, configures bus, requests OP, writes outputs zero |
| `ping` | Reads slave AL state; returns OK for all raw states equal to OP; WKC mismatch becomes an advisory warning |
| `set_output {pin,value}` | Delegates one pin to the batch write path |
| `set_outputs {outputs:[{pin,value}]}` | Validates nonempty list, coerces values to integers/booleans, checks pins 0–15, writes one packed word, then five PDO exchanges with 10 ms sleeps |
| `get_input {pin}` / `get_all_inputs` | Fresh exchange before reading packed input bits; no inversion |
| `get_all_outputs` | Returns output buffer bits and raw word; this is commanded buffer state, not independent actuator feedback |
| `enable_button_monitor {start_pin,stop_pin}` | Starts thread polling at approximately 50 ms and emits `button_press` events on changes |
| `cleanup` | Stops threads, clears outputs when initialized, requests INIT and closes master |

Requests use `{id,command,params}`; replies use `{id,result}`. Invalid JSON returns `{id:null,error}`; other exceptions become error objects. Logs go to stderr; response/event JSON goes to stdout. EOF, SIGINT and SIGTERM call cleanup. Cleanup catches exceptions, so successful process exit is not proof that the physical outputs reached zero. Evidence: bridge `scripts/ethercat_bridge.py:L470-L572`, `scripts/ethercat_bridge.py:L574-L647`, `scripts/ethercat_bridge.py:L649-L683`, `scripts/ethercat_bridge.py:L755-L846`.

`_pd_lock` serializes wire exchange and I/O buffer access. The intended maintainer period is 5 ms (200 Hz), with state checks every 100 cycles and termination after ten consecutive exceptions. `ping` explicitly treats a mismatched WKC as OK with a warning. This is an availability choice; OP state alone is not confirmation that a particular output command reached its device. Evidence: bridge `scripts/ethercat_bridge.py:L36-L42`, `scripts/ethercat_bridge.py:L78-L101`, `scripts/ethercat_bridge.py:L488-L503`, `scripts/ethercat_bridge.py:L685-L747`.

Static concerns requiring targeted validation:

1. `_start_op_state_maintainer()` is called during `init` at lines 304 and 407, but `is_initialized` becomes true only at line 422. The worker's loop at line 699 requires that flag; a thread scheduled immediately can exit before initialization completes, leaving `op_maintainer_running` true. This is a source-level startup race, not a reproduced hardware failure.
2. Initialization can select a nonzero `target_slave_pos`, but subsequent output/input methods and the maintainer use `master.slaves[0]`. A multi-slave installation can therefore configure/clear one selected slave and operate another. Evidence: `scripts/ethercat_bridge.py:L244-L268`, `scripts/ethercat_bridge.py:L410-L419`, `scripts/ethercat_bridge.py:L536-L536`, `scripts/ethercat_bridge.py:L585-L585`, `scripts/ethercat_bridge.py:L611-L611`, `scripts/ethercat_bridge.py:L638-L638`, `scripts/ethercat_bridge.py:L704-L704`.
3. `_al_state()` masks the low AL nibble for display, while health and transition predicates still compare raw `slave.state` to 8. The display can describe a flagged state as OP while health reports it unhealthy. Evidence: `scripts/ethercat_bridge.py:L60-L76`, `scripts/ethercat_bridge.py:L274-L274`, `scripts/ethercat_bridge.py:L320-L320`, `scripts/ethercat_bridge.py:L484-L484`, `scripts/ethercat_bridge.py:L720-L720`.
4. There is no local knowledge of machine door, clamp, PNOZ, reference, or production sequence interlocks inside the bridge. Its pin-write API is a transport primitive; callers own semantic interlocks. Evidence: `set_outputs`, `scripts/ethercat_bridge.py:L521-L572`.

The retained `ethercat comunication base/scripts/ethercat_bridge.py` is a different implementation, not a byte-identical alias. The active root bridge adds lock/WKC/batch-write changes. Its old GPIO bridge and printer/udev setup utilities describe a separate multi-chamber-oriented integration; their presence does not establish that current backend uses them. Do not substitute the reference bridge or GPIO pin map for the active machine mapping.

## Centring firmware: executable contract

The production entry point delegates Arduino `setup/loop` to `app::init/tick`. Initialization enables the 2 s AVR watchdog, initializes GPIO/debounce, attaches servos at compile-time start pulses, initializes the parser and starts Ethernet. The tick order is debounce → E-stop check → disconnect/keepalive handling → command parsing/session replacement → motion tick → periodic/status completion output. Evidence: firmware `Double_Actuator_Centring_Slave_Firmware/src/main.cpp:L1-L16`, `Double_Actuator_Centring_Slave_Firmware/src/app.cpp:L18-L48`, `Double_Actuator_Centring_Slave_Firmware/src/app.cpp:L51-L141`.

Pin map: upper servo D2, HOME D3, TRAVEL D4; lower servo D9, TRAVEL A0, HOME A1; software E-stop D8; RGB D5/D6/D7; ENC28J60 CS D10 with hardware SPI D11–D13. Switches use INPUT_PULLUP and pressed LOW; debounce is 25 ms. Evidence: `Double_Actuator_Centring_Slave_Firmware/include/pins.h:L12-L55`, `Double_Actuator_Centring_Slave_Firmware/src/switches.cpp:L19-L66`, `Double_Actuator_Centring_Slave_Firmware/include/board_config.h:L37-L38`.

Timing/rails: 250–2400 µs electrical pulse rails, default model move speed 45 deg/s with 0.01–120 clamp, seek steps 4 µs every 20 ms, motion timeout 60 s, receive keepalive timeout 10 s, idle PWM detach after 1.5 s, nudge hold 5 s, E-stop release hold 200 ms, maximum 128 command bytes and 48 receive bytes per tick. Evidence: `Double_Actuator_Centring_Slave_Firmware/include/board_config.h:L14-L58`, `Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L50-L50`, `Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L135-L158`, `Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L366-L385`, `Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L782-L813`, `Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L865-L872`.

Every recognized command emits one space-separated status line beginning `u=`, containing commanded angle/pulse/model height, `busy`, `cal`, `lastCmd`, `accepted`, `reason`, limits, offset, calibration ID/pulses and curve (`A`, `B`, `C`, `sHome`, `sTravel`), switch bits, `estop`, `targetH`, `moveEnd` and session counter. Model height is `nan` before valid calibration. A connection sends `READY`, `PING`, then status. Live motion status is sampled every 200 ms; completion also emits status. These are computed/commanded positions, not encoder measurements. Evidence: `Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L436-L496`, `Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L828-L844`, `Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L875-L887`; `Double_Actuator_Centring_Slave_Firmware/src/app.cpp:L111-L127`.

`kinematics` maps each pulse to normalized switch fraction `t`, maps soft angle through a quadratic, and derives total opening from both sides plus offset. Both-axis moves split requested model height equally; single-axis moves subtract the other side's current modeled height and allow 0.35 mm edge tolerance. Runtime calibration resets on MCU boot and requires the host to resend it. Evidence: `Double_Actuator_Centring_Slave_Firmware/src/kinematics.cpp:L50-L56`, `Double_Actuator_Centring_Slave_Firmware/src/kinematics.cpp:L78-L97`, `Double_Actuator_Centring_Slave_Firmware/src/kinematics.cpp:L175-L194`, `Double_Actuator_Centring_Slave_Firmware/src/kinematics.cpp:L199-L264`, `Double_Actuator_Centring_Slave_Firmware/src/kinematics.cpp:L282-L359`; `Double_Actuator_Centring_Slave_Firmware/include/kinematics.hpp:L3-L5`.

Safety-relevant details:

- Normal model moves interpolate pulses without checking HOME/TRAVEL bits during motion (`Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L224-L264`). Switch-driven seek does check its target switch. Electrical rails and a model range are not physical end-position feedback.
- If a HOME switch never releases within 400 µs of backoff, the implementation restores the start pulse and deactivates the axis; when all axes deactivate it returns `MoveEnd::Ok`. A successful completion alone therefore does not prove the expected release/reseek sequence occurred (`Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L33-L34`, `Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L182-L220`).
- A seek at an electrical rail reverses direction and continues until switch assertion or the 60 s timeout (`Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L202-L227`).
- Software E-stop detaches PWM and latches until explicit clear; the clear call reattaches at the stored pulse (`Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L120-L132`, `Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L333-L363`). The board comment says “auto-clear,” but executable logic only records release time until `clearEstopIfSafe` is invoked.
- A closed peer socket, 10 s receive silence, or new replacement client aborts running motion through `onLinkLost` (`Double_Actuator_Centring_Slave_Firmware/src/app.cpp:L60-L104`, actuators `Double_Actuator_Centring_Slave_Firmware/src/actuators.cpp:L413-L427`). This contradicts header/protocol comments claiming reconnect preserves motion (`Double_Actuator_Centring_Slave_Firmware/include/app.hpp:L3-L5`, `Double_Actuator_Centring_Slave_Firmware/include/actuators.hpp:L46-L49`, `Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L840-L842`). Executable code is authoritative.
- `onMotionComplete` emits `accepted=1` and reason OK for timeout, with `moveEnd=timeout`; consumers must inspect `moveEnd`, not just `accepted` (`Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L875-L880`).
- Float parsing accepts a numeric prefix without checking the remainder of its token; signed integer parsing does check the whole token (`Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L162-L204`, `Double_Actuator_Centring_Slave_Firmware/src/protocol.cpp:L341-L368`). Host numeric validation matters.

`tools/servo_jog/main.cpp` is an alternate USB-only firmware image with independent direct pulse, hold/pulse, sweep and edge-seek commands. It is not an API mode of production firmware. `not_used/platformio.ini` is an archived serial-only build definition; that folder has no retained implementation source in this checkout. `images/version-1` and `images/version-2` contain compiled firmware artifacts, not source equivalence proof; their contents were not read. `arduino/` is empty in this checkout. `EtherCard-main/` is vendored library material, not inspected as application source.

## Pick-and-place master and firmware gap

The Node master validates persisted motion/backoff configuration, clamps target positions between per-axis backoff and a configured maximum, and maps raw status to homed/busy/fault/alarm/position fields. Defaults are 80 mm/s move/home, 0.5/0.8 mm backoff, reference A, 470 mm maximum, with a configurable maximum no greater than 2000 mm. Source-derived steps/mm defaults to `10/3`, and `pulseMm=300` is milli-mm per step. Evidence: master `New_version_pick&place/master/pick_place_master.js:L35-L108`, `New_version_pick&place/master/pick_place_master.js:L157-L197`, `New_version_pick&place/master/pick_place_master.js:L267-L277`, `New_version_pick&place/master/pick_place_master.js:L331-L421`.

`PersistentPickPlaceTcp` keeps one connection, permits one pending transaction, matches response prefixes/command-tag errors, drops timed-out sessions, and emits unsolicited HELLO/EVENT lines. `sendCommand` serializes transactions with a promise chain. Optional transient mode creates a socket per command. Host motion calls read STATUS before issuing HOME/MOVE and reject busy, E-stop, fault, alarm, missing homing, and available limit-switch states. Minimal status can omit switches; the master then relies on the external firmware to enforce them. Evidence: master `New_version_pick&place/master/pick_place_master.js:L590-L917`, `New_version_pick&place/master/pick_place_master.js:L1085-L1249`.

`initializePickPlace` prepares the session, conditionally clears fault/E-stop, always HOMEA then HOMEB (unless single-motor mode), checks homed/backoff result, validates final flags, and releases its production hold/socket in `finally`. Recoverable home failures can retry with STOP/wait/CLRFAULT and settle. `recover()` can itself move the axes by homing them; `clearError()` only sends CLRFAULT plus STATUS. Evidence: master `New_version_pick&place/master/pick_place_master.js:L1376-L1437`, `New_version_pick&place/master/pick_place_master.js:L1870-L2050`; `New_version_pick&place/master/lib/pick_place_ops.mjs:L32-L91`.

The master sends `PING`, `STATUS`, `STOP`, `ESTOP`, `CLRFAULT`, `HOME`, `HOMEA`, `HOMEB`, `MOVEAMM`, `MOVEBMM`, and production dual-axis `MOVEAMMT2`. Command limit is 79 characters; fixed timeouts include PING 2 s, STATUS 5 s, command 15 s, individual HOME 150 s, combined HOME 270 s. MOVE timeouts grow with distance/speed and environment settings. Missing MOVE DONE can be accepted after STATUS shows a nonfaulted position within tolerance (default at least 0.5 mm); `waitIdle` failure is swallowed before that final check, and only reference-axis position is compared. Evidence: master `New_version_pick&place/master/pick_place_master.js:L164-L197`, `New_version_pick&place/master/pick_place_master.js:L556-L560`, `New_version_pick&place/master/pick_place_master.js:L1487-L1515`, `New_version_pick&place/master/pick_place_master.js:L1615-L1687`.

Two important static limits:

1. `stop()` and `emergencyStop()` use the same serialized `sendCommand` chain as a motion awaiting DONE. A software stop can be queued behind a long-running motion transaction instead of interrupting it. This needs a dedicated preemption/timing test and cannot be inferred safe from a method name. Evidence: master `New_version_pick&place/master/pick_place_master.js:L1085-L1088`, `New_version_pick&place/master/pick_place_master.js:L1141-L1141`, `New_version_pick&place/master/pick_place_master.js:L1363-L1372`.
2. `New_version_pick&place/src/main.cpp` is a 104-line stub. Its unused `handleCmd` returns canned status/DONE values; `setup` only starts Serial and `loop` only delays. It contains no TCP server, pulse generation, live sensor reads, or invoked command dispatcher. It also lacks `MOVEAMMT2`, which the master sends. A production pick-and-place firmware implementation and its build configuration are not reconstructable from this file. Evidence: stub `New_version_pick&place/src/main.cpp:L24-L99`, `New_version_pick&place/src/main.cpp:L100-L104`; master `New_version_pick&place/master/pick_place_master.js:L1511-L1515`, `New_version_pick&place/master/pick_place_master.js:L1723-L1736`. No `platformio.ini` exists in that pick-and-place root in this checkout.

The master contains unconditional debug telemetry attempts: localhost HTTP ingest requests plus append-only `.cursor` logs in an absolute project path. Mocking the Nano transport does not suppress those side effects (`New_version_pick&place/master/pick_place_master.js:L711-L720`, `New_version_pick&place/master/pick_place_master.js:L798-L817`, `New_version_pick&place/master/pick_place_master.js:L1103-L1127`, `New_version_pick&place/master/pick_place_master.js:L1649-L1673`). Debug log content was not read.

## Vision slave CLI boundary

The current shell wrapper invokes `scripts/vision_master_client.py`; root `vision_master_client.py` is a near duplicate with an older health-only ping. The scripts copy falls back from a 4 s `/health` timeout to a 10 s `/remote/info` query. Environment loading deliberately gives six vision keys from `backend/.env` precedence over shell values; no environment file was read in this audit. Evidence: `scripts/vision-master.sh:L4-L18`, scripts CLI `scripts/vision_master_client.py:L38-L106`, `scripts/vision_master_client.py:L145-L159`; root CLI `vision_master_client.py:L145-L149`.

Operations include reading remote info/programs, capturing camera frames, registering master images, creating tool templates, recovering the camera, deleting programs, running inspections, and live Socket.IO inspection/feed subscriptions. Capture saves local image bytes; master registration uses multipart upload and cleans temporary capture files; run-once may save inspection JPGs; delete can fall back from remote-key endpoint to local-key endpoint after 401/403. Socket mode emits `start_inspection` and `subscribe_live_feed`, then unsubscribes/stops/disconnects in `finally`. These are remote mutations, not offline examples. Evidence: scripts CLI `scripts/vision_master_client.py:L172-L345`, `scripts/vision_master_client.py:L348-L420`.

HTTP timeouts range from 4 s health to 120 s for registration, recovery, deletion and inspection. External vision implementation is outside this source tree; response semantics and actual camera behavior are not established by this client. The `/api/v1` Socket.IO root stripping removes only the final segment (`scripts/vision_master_client.py:L355-L357`), so that base becomes `/api`; whether the slave accepts that path is unverified.

## Maintenance boundaries and related references

Firmware uploads, jog tools, EtherCAT diagnostics, calibration suites, and production soak scripts are side-effecting operations. Their test-selection and isolation requirements are recorded in [testing and validation](15-TESTING-AND-VALIDATION.md). Build hooks can patch dependency/framework source outside application files; service installers can modify the host. See [configuration and deployment](13-CONFIGURATION-AND-DEPLOYMENT.md).

Limitations: this document does not certify E-stop hardware, PNOZ relay wiring, air/heater limits, ultrasonic welding parameters, motor calibration, external APIs, or flashed firmware. Source-level interlocks describe software intent and concrete code paths only. Retained PDF/manual/binary assets, secrets, production database records, captures and historical explanatory documentation were excluded from inspection.
